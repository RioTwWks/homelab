# Черновик серии статей для Habr

Идея: не “идеальный туториал”, а **практический дневник сборки** домашнего голосового хаба на Linux — с тем, что ломалось, почему, и к каким компромиссам пришёл.

Важно: медиа‑плееры/торренты — **один из модулей**, а не центр проекта. Центр — голосовой контур + детерминированные интенты + воспроизводимый деплой.

Нотация для вставок:
- `[Рисунок N: ...]` — что за картинка/скрин и куда её поставить
- `[Листинг: ...]` — код/конфиг, который лучше показать в статье
- `[Врезка: ...]` — короткий “грабли/урок/почему так”

## Серия (план, без перекоса на один модуль)

### Часть 1. Архитектура и MVP: голос → интенты → действия
Фокус: как разложить систему на Docker‑сервисы и host‑часть, чтобы получить первый работающий контур.

### Часть 2. Голосовой контур: STT (Whisper) + TTS (Piper/Silero) + wake word
Фокус: почему начинать с push‑to‑talk, как “прогреть” STT через whisper‑server, как выбрать TTS и детектор wake word.

### Часть 3. Детерминированные команды: media-api + executor (kiosk/CDP, Kodi, MPRIS)
Фокус: быстрые команды без LLM, контроль браузера в kiosk, Kodi JSON‑RPC и управление музыкой через MPRIS.

### Часть 4. Умный дом: Home Assistant API и безопасность токенов
Фокус: маппинг фраз на домены/сущности HA, как не тащить LLM в управление светом/климатом.

### Часть 5. “Homelab‑сервисы”: Nextcloud + Immich + доступ извне
Фокус: “своё облако” и “своё фото”, версии образов, миграции, доверенные домены, доступ с телефона.

### Часть 6. Надёжность данных: RAID + бэкапы по расписанию
Фокус: куда класть docker‑тома, как бэкапить всю систему (не только “файлы”), как восстановиться.

### Часть 7 (опционально). Торренты и медиа‑эксперименты как модуль
Фокус: варианты “скачал и смотри” и “стриминг”, и разбор граблей (портовые конфликты, VPN/прокси в контейнерах, индексеры) — как пример инженерного дебага.

### Часть 8 (опционально). Roadmap: улучшение голоса, инструментов и самого сервера
Фокус: как развивать систему после MVP: качество STT/TTS, обучение wake word/голоса, новые интенты, “операционка” (обновления/наблюдаемость/бэкапы).

### Moltbot Web UI как “главный экран” сервера
Чтобы у проекта был **презентабельный интерфейс** (и чтобы быстро получать доступ ко всем сервисам), добавил `moltbot-ui` — небольшой web‑портал, который:
- даёт **чат** к `moltbot-api` (плюс история по сессиям в localStorage),
- умеет **быстрые команды** (кнопки) и **голосовой ввод** прямо из браузера,
- показывает **дашборд сервисов** (карточки “Открыть” + online/offline/unknown) и **статусы** (`/v1/system/status`),
- проксирует `/api/*` и `/docs` под тем же origin (убираем CORS, удобнее шарить ссылку внутри LAN).

Для проверки сервисов дашборда добавил `POST /v1/system/services`: UI отправляет список URL, а бэкенд пингует их из docker‑сети и возвращает результат.

### Почему команды “пауза/свет” не должны идти через LLM
- скорость
- предсказуемость
- безопасность (LLM не “интерпретирует” команду творчески)

Фактически: маппинг фраз → `action/target` → вызов `media-api` или HA API.

## Часть 8 (опционально). Roadmap: куда развивать систему дальше (каркас)

Цель этого блока — закрепить, что “всё работает” — это только начало. Дальше начинается самое интересное: качество голоса, устойчивость, удобство и “операционка”.

[Рисунок 12: Roadmap]

### 8.1 Улучшение голосовых команд (NLU/интенты)
- Вынести фразы/синонимы/правила в отдельный конфиг (или YAML), чтобы добавлять команды без правок кода.
- Добавить “подтверждение” для опасных действий (выключить весь свет/перезапуск сервисов).
- Развести пересечения интентов (например “температура” как погода vs климат).
- Добавить команды “уровнем выше”: сцены и скрипты Home Assistant (“режим кино”, “спать”).

[Врезка: “лучше 30 предсказуемых команд, чем 300 ‘иногда’”]

### 8.2 STT: качество/скорость/шум
- Подобрать модель Whisper под железо (реальное время важнее идеального качества).
- Прогретый STT через `whisper-server` + системный автозапуск.
- Шумоподавление/AGC, автодетект тишины, настройка микрофона.
- “Barge-in”/echo‑guard: отключать микрофон на время TTS, чтобы ассистент не “слушал сам себя”.

[Рисунок: график/таблица “модель → скорость/качество” (можно 2–3 строки, без бенчмарков до миллисекунд)]

### 8.3 TTS: голоса, естественность, кастом
- Выбрать базовый RU‑голос (Piper или Silero) и сделать “профили” (нейтральный/ночной).
- Нормализация чисел/дат (чтобы “2.14” звучало адекватно).
- Дальше — эксперименты с новыми голосами/обучением (если будет запрос).

### 8.4 Wake word: обучение и режимы
- Обучить свою русскую фразу в openWakeWord: позитивные/негативные примеры под домашний шум.
- Отдельные режимы (день/ночь), пороги, cooldown.
- Метрики ложных срабатываний и “время до реакции”.

### 8.5 Изучение возможностей Moltbot и внедрение “по уму”
- Память: использовать Redis/Qdrant для “настроек пользователя” и устойчивого контекста (город, устройства, предпочтения).
- Инструменты: системные статусы сервера, уведомления, интеграции (MQTT/HA).
- Строгие форматы ответа для отдельных интентов (JSON‑схемы уже используются в проекте).

[Листинг: пример “tool-only” пути из `moltbot_api/app/main.py` (где медиа/HA возвращаются без LLM).]

### 8.5.1 Roadmap UI: превратить Moltbot Web UI в полноценный homelab‑портал
- карточки всех сервисов с группировкой/поиском/быстрыми ссылками (как “домашняя стартовая страница”)
- расширенные статусы: причины деградации (таймауты, коды ответов), uptime, версия контейнера/образа
- “быстрые действия” с подтверждением: перезапуск сервиса, запуск/остановка профиля, сценарии Home Assistant
- отдельный “режим для скринов” (скрыть чувствительные данные)

### 8.6 Roadmap сервера: обновления, наблюдаемость, безопасность
- Healthchecks и алерты на падение ключевых контейнеров.
- Централизованные логи (хотя бы единый каталог + ротация; дальше — стек наблюдаемости).
- Управление секретами: не хранить токены “где попало”, минимизировать экспорт env.
- Автообновления с контролем: окно обновлений + откат.
- Регулярный тест восстановления из бэкапов.
- **Тесты (pytest):** написать тесты для moltbot-api (healthz, system/status, system/services, при желании chat с моками), по возможности — для media-api; структура `moltbot_api/tests/` или `tests/`, команда `pytest`.
